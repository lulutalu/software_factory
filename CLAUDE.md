# CLAUDE.md: software-factory

This repo is a **Claude Code plugin** (not an application). It ships one skill (`factory`) and seven subagents that together form a multi-agent dev pipeline. User-facing docs are in `README.md`.

## Layout
- `.claude-plugin/plugin.json`: plugin manifest (name `software-factory`)
- `.claude-plugin/marketplace.json`: local marketplace `software-factory-local`, so the plugin can be installed with `/plugin install`
- `skills/factory/SKILL.md`: the **orchestrator**. It runs in the user's main session.
- `ui/server.py`: dashboard server (Python stdlib, 127.0.0.1). GET `/api/state`, `/api/file?path=`; the only write is POST `/api/answer`
- `ui/wait_answer.py`: background watcher the orchestrator starts while a question is pending; exits 0 on a browser answer, 3 when cancelled
- `ui/index.html`: dashboard page (vanilla JS, no external assets, polls every 2s)
- `agents/*.md`: subagents: `spec-writer`, `builder`, `frontend`, `backend`, `data`, `tests`, `code-reviewer`, `security-reviewer`
- `tests/`: stdlib `unittest` suite. `test_server.py` (verdict parser, answer validation, HTTP security checks on a real server on a free port), `test_plugin.py` (manifests, agent frontmatter: name/model/effort, no `Edit` on read-only roles, SKILL.md references every agent, builder lists every specialist)
- `.github/workflows/ci.yml`: GitHub Actions on push to main / PRs: tests on Python 3.10 and 3.13, the example's generated tests (`pip install -e ".[test]"`, pytest, `todo --help`), and `claude plugin validate .` (CLI pinned to `@anthropic-ai/claude-code@2.1.328`; validate works without login). CI never runs the agents (would need an API key, non-deterministic).
- `LICENSE`: MIT (also `license` in `plugin.json`)
- `examples/todo-cli/`: output of the first real run (2026-11-19, request: Python CLI todo app). `.factory/` audit trail + the generated code, copied from a scratch project with local paths replaced by `<project>` (`ui.json`, `pending.json`, caches left out). `.gitignore` re-includes `examples/*/.factory/`. CI installs it and runs its pytest suite. Don't edit it by hand: it's a record of what the agents produced.
- `docs/images/`: dashboard screenshots from that run (questions, pipeline/reviews, approval), used in the README. Crop them so no local path is visible.

## Key design decisions
- **Orchestration lives in the skill, not in an agent.** Subagents cannot spawn subagents, so the main session (driven by `SKILL.md`) dispatches every step. The builder is a *planner* only; it never writes production code.
- **No SDK.** Everything is native Claude Code (skill + subagents). The Agent SDK would only be needed to run outside a Claude Code session (server, webhook, CI orchestrator).
- **File-based handoffs** in the target project's `.factory/` directory (`spec.md`, `plan.md`, `reports/round-N/`, `review-code.md`, `review-security.md`, `log.md`). Subagents start with no context, so files are the shared memory and the audit trail.
- **Machine-parsed formats:** the orchestrator parses `plan.md` (the `specialist:` / `wave:` / `files:` fields per task) and the first line of both review files (`VERDICT: APPROVED | CHANGES_REQUESTED`). If you change these formats in an agent, update `SKILL.md` too.
- **Parallel safety:** tasks in the same wave run in parallel, and the builder must give them disjoint `files:` lists. Specialists may only edit the files they own.
- **Spec questions go through the orchestrator:** subagents can't ask the user, so spec-writer lists *Open questions* and the skill asks them (max 2 passes).
- **Two reviewers in parallel:** `code-reviewer` (spec, tests, correctness, maintainability) and `security-reviewer` (vulnerabilities). They don't overlap: the code-reviewer leaves security out. A round passes only if both approve. They replaced the single `reviewer` agent.
- **Loop:** at most 2 build/review rounds (changed from 3), then user approval (Approve / Request changes = +1 round / Reject). An extra round raises `max_rounds` in `status.json` to that round's number.
- **Plan validation:** before dispatching, the orchestrator checks `plan.md` (valid `specialist:`, positive integer `wave:`, non-empty `files:`, no file shared by two tasks in the same wave). If it fails: one builder re-run with the exact problems, then ask the user. The orchestrator never edits the plan itself.
- **Verdict parsing (shared rule, SKILL.md and `ui/server.py` `first_verdict`):** skip blank and ```` ``` ```` lines; the first remaining line must match `VERDICT: APPROVED|CHANGES_REQUESTED` (case-insensitive); only that line counts. Unparseable → re-run that reviewer once, then treat it as CHANGES_REQUESTED and tell the user. The dashboard shows `INVALID`. Keep the two implementations in sync.
- **Live dashboard:** `/factory` starts `ui/server.py` in the background via `${CLAUDE_PLUGIN_ROOT}` and writes `.factory/status.json` (format defined in `SKILL.md`) at every change of step, round, task or review. Verdicts are read directly from the review files' first line.
- **Answering from the browser (two-way, chosen by the user; reverses the earlier read-only decision):** only the **spec open questions** and the **final approval** can be answered from the page. Other prompts (archive, invalid plan) stay terminal-only. Flow (*Asking the user* in `SKILL.md`): the orchestrator writes `.factory/inbox/pending.json`, asks in the terminal as plain text (no AskUserQuestion, which would block), starts `ui/wait_answer.py` in the background and ends its turn. The browser POSTs the answer, the server writes `inbox/answer.json`, the watcher exits and the orchestrator is re-invoked. A terminal reply also works: the orchestrator deletes `pending.json`, which stops the watcher. First answer wins (server lock + 409). Answered questions are moved to `inbox/answered/<id>.json`. No dashboard running → plain AskUserQuestion.
  - POST checks: Host is `127.0.0.1:<port>`/`localhost:<port>` (DNS rebinding; also enforced on GET), `Origin` equals that host (CSRF), `X-Factory-Token` equals a per-server random token that is never written to disk (injected into the served page in place of `__FACTORY_TOKEN__`), `Content-Type: application/json`, body ≤ 64 KiB, and the answer is validated against `pending.json` (id must match; only listed options; single-choice limited to one; text ≤ 8000 chars; feedback required for `request_changes`). Only the validated fields are written.
  - Formats of `pending.json` / `answer.json` are defined in `SKILL.md`; `validate_answer` in `server.py` and the forms in `index.html` must stay in sync with them.
  - Security: binds 127.0.0.1 only; the only write is POST `/api/answer` (above); serves only `.md`/`.json` files inside `.factory/` (resolved-path check), agent text is HTML-escaped before the minimal markdown rendering (no links or raw HTML).
  - Lifecycle: writes `.factory/ui.json` (url, pid), tries ports 8765–8784, exits after 30 min with no requests. SIGTERM (`kill <pid>`) is handled like a normal stop, so `ui.json` is removed (before, it was left behind pointing to a dead PID).
- **Model tiers (chosen by the user, "Balanced"):** opus/high for spec-writer, builder, code-reviewer, security-reviewer (judgement roles); sonnet/medium for frontend, backend, data, tests (precise task execution, often several in parallel, so most of the token spend). The `/factory` skill is deliberately left unpinned and follows the session's `/model`. The skill tells the orchestrator never to pass `model`/`effort` to the Agent tool, because that would override the frontmatter. Aliases (`opus`, `sonnet`) track the latest model of each family. `claude plugin validate` does not check `model`/`effort` values; an invalid effort only logs a warning (checked in Claude Code 2.1.322).
- **Never commits.** No agent or step runs `git commit`/`push`; the user commits. The skill only suggests a commit message.

## Conventions
- Agent frontmatter: `name`, `description`, `tools`, `model`, `effort`. Read-only roles (spec-writer, builder, code-reviewer, security-reviewer) get no `Edit`. Only the two reviewers get `Bash`, to run tests and audit tools.
- Plugin agents are referenced as `software-factory:<agent>` in the skill.
- Validate after any change: `claude plugin validate .` and `python3 -m unittest discover -s tests`. If you add an agent or a model/effort value, `tests/test_plugin.py` must still pass.
- `.gitignore` excludes run output (`.factory/`, `.factory-archive/`), Python caches, Playwright artifacts (`.playwright-mcp/`), `.claude/settings.local.json` and secret files. Put test runs of the pipeline in a scratch project, not in this repo.

## Ongoing work / status
- v0.2.0 (`plugin.json`). The GitHub repo is being prepared as a portfolio piece (job application: agentic AI / agent platform engineer). The README is written for that reader: it presents the project as a **proof of concept**, with a *Design decisions* table and a *Limitations and next steps* section. Keep that framing honest when the status changes.
- Verdict rules (set by the user). The reviewers only drive the loop; the user has the final say.
  - code-reviewer blocks on: test failures; spec not fully implemented (any R missing, any A failing or unverifiable); specialist *Notes / blockers* not `None` (tool warnings in *Checks run* are non-blocking); correctness bugs; serious maintainability problems (duplication, dead code, ignoring conventions). Style and naming are non-blocking.
  - security-reviewer blocks on: any Medium/High/Critical finding. Low/Info are non-blocking.
- **First real run done (2026-11-19, `examples/todo-cli/`):** spec (10 open questions, answered from the dashboard) → round 1 (4 tasks, 2 waves; tests specialist correctly reported a blocker when pytest was missing) → code review CHANGES_REQUESTED on a real bug (C1, `Path.exists()` hiding permission errors) while security approved → round 2 planned only the fix → both approved → user approved in the terminal. Plan validation, the 2-round loop, parallel reviewers, the dashboard and the browser answer path all worked in practice.
  - Observed issues to work on: the spec-writer asks too many questions (10 for a small CLI); the orchestrator asked extra terminal confirmations not in `SKILL.md` ("4 derived points", "builder's 5 choices"); it also told the code-reviewer to treat an unverifiable criterion (A1, no pip in the environment) as non-blocking, which the verdict rules don't provide for.
- Dashboard tested by hand on fake `.factory/` data (rendering, live updates, path traversal, escaping) and during the first real run.
- Browser answers tested on a mock `.factory/` (curl: missing/wrong token, cross-site Origin, rebinding Host, wrong content type, oversized body, stale id, invalid options, double answer → all refused; Playwright: approval form, error message, successful answer; watcher exit 0 and 3; SIGTERM cleanup). The orchestrator side worked in the first real run (spec questions answered in the browser, approval in the terminal). Open point still partly visible: after the browser answer the orchestrator asked for extra terminal confirmations (see above).
- Plan validation and the 2-round loop were exercised in the first real run; the verdict re-run (unparseable verdict) has not been triggered yet. The tolerant `first_verdict` parser is covered by `tests/test_server.py`.
- Known limitation: archiving `.factory/` doesn't stop a dashboard from a previous run; it times out on its own.
- Decided: MIT license. CI = checks only (no demo workflow running the agents).
